# Предварительный отчёт: сопоставление старых заказов для CRM

**Дата проверки:** 25 октября 2026 г.  
**Источник:** read-only выборка из существующей таблицы `orders` в Supabase.  
**Персональные данные:** телефоны, имена и адреса не выводились и не сохранялись в этом отчёте.

## Результаты

| Проверка | Результат |
|---|---:|
| Всего заказов | 2 |
| Статусы | 2 завершённых |
| Заказы без нормализуемого телефона | 0 |
| Заказы доставки | 1 |
| Заказы доставки без сохранённого адреса | 0 |
| Группы повторяющегося нормализованного телефона | 0 |
| Телефонные группы с разными именами | 0 |
| Адресные группы с разными телефонами | 0 |
| Старые e-mail | недоступны в текущей схеме заказов |

## Предварительное решение по связыванию

В выборке нет повторяющегося телефона, поэтому ни одну пару заказов нельзя
надёжно связать в одного клиента по имеющимся данным. Адрес доставки встречается
только в одном заказе, так что адресных кандидатов тоже нет. Рекомендуется
создать CRM-записи без автоматического связывания этих заказов; администратор
сможет связать их позже после ручной проверки.

Этот вывод не означает, что два заказа принадлежат разным людям: исходные данные
просто не дают безопасного основания объединить их. Все новые `customer_id`,
`customer_phone_id` и `delivery_address_id` для старых заказов должны оставаться
`NULL`, пока не будет ручного подтверждения. Имена, телефоны, адреса, суммы,
статусы и время старых заказов не переписываются.

## Замечания по качеству данных

- В текущей схеме `orders` есть поля `customer_name`, `customer_phone`,
  `pickup_type`, `street`, `house_number`, `postal_code`, `city`, `floor`,
  `subtotal`, `delivery_fee`, `total`, `status`, `created_at`.
- Необязательный e-mail можно хранить в профиле клиента; индекс по его
  нормализованному виду также остаётся неуникальным и не используется для
  автоматического объединения людей.
- Форма отправляет адрес, время и примечание доставки в `/api/orders`, однако
  текущий обработчик сохраняет в `orders` только имя, телефон, тип получения и
  суммы. Поэтому полнота адресов в этой выборке не гарантирует, что последующие
  заказы будут сохраняться так же: обработчик заказа следует дополнить отдельным
  изменением приложения до включения CRM-сопоставления.
- Нормализация номера для этой предварительной выборки учитывала международный
  префикс и немецкий национальный формат (`0…` → `+49…`). Для продукта нормализатор
  должен использовать настраиваемую страну ресторана; неоднозначные варианты
  нельзя связывать автоматически.
- Сравнение адресов использовало почтовый индекс, город, улицу, номер дома и
  дополнительную строку адреса после Unicode NFKC, приведения регистра и
  схлопывания пробелов/пунктуации. Совпадение адреса только формирует кандидата,
  но не объединяет клиентов.

## Доступ и RLS

- Read-only запрос публичным ключом к `orders` и `order_items` завершился ошибкой
  PostgreSQL `42501`; доступ на чтение через anon не предоставлен.
- Точные определения действующих RLS-политик и grants нельзя получить через
  используемый PostgREST API. Read-only запросы к `pg_policies`, `pg_class` и
  `information_schema.role_table_grants` вынесены в
  `supabase/checks/customer_crm_preflight_and_audit.sql`; сохраните baseline
  агрегатов, контрольные суммы и `max_order_id` до любой миграции. После
  отдельно одобренной миграции сравните baseline, посчитайте CRM-связи для
  старых и новых заказов и проверьте запросы несоответствий в том же файле.
- Текущие админские страницы и API заказов/статусов проверяют пользователя через
  `getAdminUser()` и `ADMIN_EMAILS` до операций с `SUPABASE_SECRET_KEY`.
- Публичный `/api/orders` использует `SUPABASE_SECRET_KEY` без админской сессии,
  поскольку это гостевой checkout. Сейчас он проверяет базовые поля, но принимает
  цены и суммы от браузера. Перед будущим CRM-релизом этот публичный путь нужно
  отдельно ограничить серверной проверкой меню/цен и защитой от злоупотреблений;
  CRM API должны требовать `getAdminUser()` на каждом запросе.

## Что остаётся проверить вручную до миграции

1. Сверить read-only preflight из
   `supabase/checks/customer_crm_preflight_and_audit.sql` с фактическими RLS и
   grants; записать baseline и границу `max_order_id`.
2. Подтвердить формат адресной нормализации, включая `floor`/квартиру, и страну
   по умолчанию для телефонов.
3. Просмотреть исходные заказы в админке и вручную подтвердить любые будущие
   связи; для текущих двух заказов безопасных автоматических связей нет.
4. Согласовать CRM-модель и только затем отдельно разрешить выполнение
   `supabase/migrations/202610250001_customer_crm_draft.sql`.

Файл preflight/audit содержит только `SELECT`: он не сохраняет baseline в базе,
поэтому сохраните результат до миграции отдельно и подставьте записанный
`max_order_id` в post-migration запросы. Адресная запись может быть общей для
нескольких клиентов через `customer_delivery_addresses`; совпадение адреса
создаёт только кандидата на проверку. CRM-связи старых заказов остаются `NULL`
до ручного подтверждения.

## Проверка функций приложения после будущего внедрения

После согласования схемы и отдельной реализации приложения проверить в тестовой
среде (не создавать тестовые данные в рабочей базе):

1. Оформить заказ через сайт и убедиться, что сумма и позиции заказа сохраняются,
   а имя, телефон, тип получения и все введённые поля доставки остаются снимком в
   самом заказе.
2. Войти в админку, изменить статус заказа, обновить страницу и подтвердить, что
   новый статус сохранён.
3. Открыть `/admin/stats`, переключить «Сегодня», «7 дней», «30 дней» и «Весь
   период»; проверить завершённые заказы, выручку, средний чек, отмены и ассортимент.
4. Выйти из админки: `/admin`, `/admin/stats` и новые CRM API должны отказать
   гостю; после входа разрешённый `ADMIN_EMAILS` пользователь получает доступ.
5. Проверить CRM-поиск: один точный телефонный кандидат, несколько кандидатов по
   телефону, совпавший адрес при другом телефоне, и параллельную отправку двух
   одинаковых заказов. Неоднозначные совпадения остаются на ручную проверку.
