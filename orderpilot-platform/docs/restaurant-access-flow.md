# Доступ сотрудников к кабинету ресторана

**Статус:** проект сценария. Не подключён провайдер авторизации, письма не отправляются, база и политики доступа не изменяются.

## Цель

У каждого сотрудника одна учётная запись платформы и отдельное членство для каждого ресторана, где он работает. После входа сотрудник видит только кабинеты ресторанов, к которым у него есть активное членство. URL кабинета сам по себе не даёт доступ.

## Поток первого доступа

1. Владелец или менеджер с правом управления персоналом открывает раздел «Сотрудники» в кабинете ресторана.
2. Указывает рабочий email и роль (`manager` или `staff`). Приглашение привязано к одному `restaurant_id`, имеет срок действия и одноразовый случайный токен; хранится только хэш токена.
3. Владелец передаёт приглашение сотруднику через выбранный ими канал. На прототипном этапе отправки нет: экран может только показать демонстрационную ссылку для ручного копирования.
4. Сотрудник открывает приглашение, входит или создаёт платформенный аккаунт, проверяет название ресторана и принимает приглашение.
5. Сервер атомарно помечает приглашение использованным и создаёт `restaurant_membership` для вошедшего пользователя. Нельзя принять истёкшее, отозванное или уже использованное приглашение.
6. После входа сотрудник попадает в список доступных ресторанов, а затем в выбранный кабинет. При членстве только в одном ресторане разрешён переход сразу в него.

## Поведение действующего пользователя

- Вход по email через выбранный провайдер платформенной авторизации; ресторан не задаётся в открытой форме как доказательство доступа.
- Список кабинетов строится по активным членствам текущего `auth.users.id`.
- Попытка открыть `/restaurant/{slug}` без членства возвращает отказ/страницу «Нет доступа»; не раскрывает внутренние настройки и заказы.
- Сотрудник, у которого есть несколько членств, переключается только между ресторанами из своего списка.
- Отключение членства немедленно запрещает новые запросы. Критичные изменения ролей и владения попадают в журнал аудита.
- Восстановление аккаунта выполняет провайдер авторизации; телефон клиента не используется как способ входа сотрудника.

## Границы ролей

| Действие | `owner` | `manager` | `staff` |
|---|---:|---:|---:|
| Просматривать и обрабатывать заказы своего ресторана | Да | Да | Да, в пределах разрешённых операций |
| Предлагать время и обновлять операционный статус | Да | Да | По настройке ресторана |
| Редактировать меню, часы и рабочие настройки | Да | Да | Нет |
| Приглашать сотрудников и назначать роли | Да | Только если владелец явно включил это право | Нет |
| Снимать/назначать владельца | Только отдельный защищённый процесс | Нет | Нет |

Каждый API-вызов проверяет текущего пользователя, активное членство, ресторан и разрешение. Скрытие кнопки в интерфейсе не является проверкой доступа. `restaurant_id` из формы или URL не считается доверенным основанием.

## Маршруты интерфейса

- `/restaurant/login` — вход или восстановление доступа.
- `/restaurant/invitations/{token}` — проверка и принятие приглашения после входа.
- `/restaurant` — список доступных ресторанов пользователя.
- `/restaurant/{slug}/orders` — очередь заказов выбранного ресторана.
- `/restaurant/{slug}/team` — управление сотрудниками по роли.

Текущие `/restaurant` и `/restaurant/{slug}` остаются демонстрационными маршрутами: список ресторанов открыт всем, а фильтр по slug — только интерфейсный. Не использовать их как модель реальной безопасности.

## API после отдельного согласования реализации

- `POST /api/restaurant/invitations` — создать приглашение после проверки права владельца/менеджера.
- `POST /api/restaurant/invitations/{token}/accept` — принять приглашение вошедшим пользователем.
- `GET /api/restaurant/memberships` — получить только собственные активные членства.
- `DELETE /api/restaurant/memberships/{membershipId}` — отключить сотрудника, если текущая роль это разрешает.
- `GET /api/restaurant/{slug}/orders` — получить заказы только после проверки членства в этом ресторане.

## Что требуется решить перед реализацией

1. Провайдер аутентификации и допустимые способы входа сотрудников.
2. Кто может приглашать персонал и может ли менеджер назначать других менеджеров.
3. Срок действия приглашения и процедура передачи владения рестораном.
4. Какие действия разрешены роли `staff` и какие изменения требуют журнала аудита.
5. Шаблоны уведомлений о приглашении, канал доставки и требования к согласию. Ничего не отправлять до отдельной настройки и реализации.

Перед подключением к staging нужна схема членства, RLS и проверки межресторанного доступа. До этого файл служит спецификацией UX/API, а не готовой системой авторизации.
